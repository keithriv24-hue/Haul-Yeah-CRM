## P0 — DEPLOY 1. Critical.

### P0-1. Remove the `crew = 3 × trucks` override  ← ROOT CAUSE, fix first

**Bug — confirmed in source, `frontend/src/lib/scopeEngine.js:312`:**

```js
let crewRec = schedMH < 12 ? 2 : schedMH < 24 ? 3 : 4;
if (trucks >= 2) crewRec = 3 * trucks;        // <-- DELETE THIS LINE
```

This one line causes every crew mismatch in the run. Case 1 (the only single-truck case) matched to the dollar; every mismatch had `trucks >= 2` and crew landing on exactly `3 × trucks`.

**Fix:**
- **Delete line 312.** Crew comes from the `schedMH` tiers plus the existing floors below it. Truck count must never set crew.
- Keep the floors that already work and sit directly beneath it: the 3BR+ `crewRec = max(crewRec, 4)` rule, and `customCrewFloor` (the heavy-item safety floor from `CUSTOM_BANDS`, 3 for 300–499 lb and 4 for 500–799 lb / stairs).
- **Add day-length escalation** (new): if `onsite = schedMH / crew` exceeds `maxHoursOnSite (10)`, raise crew toward `schedMH / targetHoursOnSite (8)`, capped at `maxCrewPerDay (12)`. If still over 10 hours at max crew, offer a multi-day split (P1-5).

Note that a large crew is not itself wrong — an 80 man-hour POD load genuinely needs ~10 people to finish in a day. The bug is that 12 was derived from phantom trucks and dragged a 4× trip fee with it.

**A correction to an earlier report — do not chase this.** An earlier draft asked you to hunt for a second truck→man-hours coupling, because Case 2 produced 32.2 billable man-hours against an expected 28.17. **There is no such coupling.** `billMH = volMH + itemMH`, and neither term reads `trucks` or `crew`. The 4.03-hour gap is exactly one Standard bedroom (190 cu ft × 2.1 ÷ 100 = 3.99 mh): the test script said "3BR house" but instructed *Standard bedroom ×2*, which is four bedrooms, while the expected values were computed for three. **The engine's man-hour math is correct.** Ignore that earlier instruction.

### P0-2. Labor-only jobs must never compute trucks

**Bug:** a labor-only job (loading a customer's POD, 0 miles, no truck) displayed **"4 trucks required," crew 12, and a $300 trip fee** — the labor-only trip fee multiplied by 4 phantom trucks.

**Confirmed in source, `scopeEngine.js:290` and `:333`:**

```js
const trucks = Math.max(1, Math.ceil(cf / TRUCK_CF), Math.ceil(lbs / TRUCK_LBS));  // no jobType guard
const travel = tripFee * trucks;                                                   // multiplies the fee
```

**Fix — and mind this trap:** `trucks` is floored at 1 and is what bills the trip fee. Setting `trucks = 0` for labor-only would **zero the trip fee**, which is also wrong — a labor-only job still charges $75. Split the concept in two:

- `displayTrucks` = `0` when `jobType === 'labor'`. Drives the "N trucks required" banner and the truck-fill graphic — both must disappear entirely on labor-only.
- `billableTrips` = `1` when `jobType === 'labor'`; otherwise the existing volume/weight calculation. This is what multiplies the trip fee.

Volume and weight still drive man-hours exactly as they do today — that part is correct and must not change.

### P0-3. Specialty-only jobs must ignore package hour floors

**Bug — worst result in the run:** one treadmill, labor-only, with the 3BR package left selected, quoted **$2,075**. The screen showed a calendar block of **0.6 hours** while billing **24 man-hours**, noting "6-hour minimum applied — 3BR+ moves never bill under it." A one-treadmill move should price around **$650** (3-man minimum × 2-hour labor-only minimum, plus capped handling). Quoting $2,075 loses the job and damages trust.

**Confirmed in source.** Two separate mechanisms leak the package into a job that has no rooms:

```js
// scopeEngine.js — package beds leak into the hour floor even with zero rooms scoped
const bedsEff  = Math.max(beds, pkgDef ? pkgDef.beds : 0);
const hourFloor = bedsEff >= hardBeds ? Math.max(hardHours, minHours) : minHours;
billMH = Math.max(billMH, hourFloor * Math.min(crew, 4));
```
```js
// ScopeCalculator.jsx:182-184 — selecting a package also writes BOTH overrides
setPkg(k);
setCrewOverride(Number(P?.[def.crewKey]) || null);    // 3BR -> crew 4
setHoursOverride(Number(P?.[def.hoursKey]) || null);  // 3BR -> 6.5 hrs
```

`specialtyOnly` is already derived correctly in the engine (no rooms scoped + at least one item or custom item). Use it.

**Fix — the package must be ignored ENTIRELY on a specialty-only job, not just its hour floor:**
1. When `specialtyOnly`, treat `bedsEff` as `0` so `hourFloor` falls back to `minHours` (2 labor / 3 truck).
2. When `specialtyOnly`, **also drop the package's `crewOverride` and `hoursOverride`.** Crew must come from `customCrewFloor` (the item's own safety floor).
3. Show an inline warning: *"No rooms scoped — package sizing ignored, pricing as specialty-only."*

**Step 2 is not optional, and this is the most likely way to half-fix this.** Suppressing only the hour floor leaves the package's `crewOverride = 4` in place, which yields `billMH = 2 × 4 = 8` and a **$850** quote. Dropping the package completely yields crew 3 (the treadmill's own floor), `billMH = 2 × 3 = 6`, and the correct **$650**. Both beat $2,075; only one is right.

**Related, keep as a separate improvement:** even on a normal household job, selecting a package silently overwrites a manually entered "Hours on site" (line 184), visible only via a small "reset" link. Write to hours only when the field has not been manually edited, and label it clearly: *"Hours set by 3BR package — reset."*

### P0-4. Assessment-required scopes must be savable

**Bug:** on the 800 lb+ blocker the rail instructs the user to *"Save the scope so nothing is lost — the number comes after someone lays eyes (and a tape measure) on it."* **The Save button is disabled.** The UI instructs an action it forbids, and the lead is lost.

**Root cause is subtler than "blocked scopes can't save"** — `ScopeCalculator.jsx:975`:

```js
disabled={saving || (r.cf === 0 && !pkg) || gate.blocked}
```

`hasBlockers` is **not** in that condition. Save is disabled because `r.cf === 0`: a blocked band returns early in the engine (`if (band.blocked) { blockers.push(...); return; }`) **before** adding its cubic feet, so an 800 lb+ item contributes nothing and the scope reads as empty.

**Fix:** treat a scope carrying blockers as non-empty. Allow save when `r.blockers.length > 0` even with `r.cf === 0`, and store it as status `assessment_required`:
- Saves all entered scope detail and the customer label.
- Appears in Saved Scopes and in the Leads pipeline flagged "On-site assessment required."
- Never displays or stores a dollar amount.

Price suppression stays exactly as it is. Only the save path changes.

## P1 — DEPLOY 2. Accuracy and coverage.

### P1-1. Payload overage — warn and let the owner choose

**Problem:** a normal 3BR with a piano (1,460 cu ft, 9,770 lb) silently became a 2-truck job because estimated weight crossed the 9,000 lb payload — while volume alone fit one truck (1,500 cu ft usable). Real operations run one truck on two trips for a local move.

**Fix — never auto-split. Volume and weight must behave differently:**

**Case A — VOLUME exceeds truck capacity (hard).** The load physically will not fit. Show a required choice:
- **Banner:** *"Load exceeds one truck by volume. Choose how to run it."*
- **Option 1 — 1 truck, 2 trips.** Offered only when one-way distance ≤ `shuttleMaxMiles (30)`. Adds return drive time as man-hours: `(2 × oneWayMiles / avgDriveMph) × crew`. No second trip fee, no extra crew.
- **Option 2 — 2 trucks.** Adds a second trip fee and a second driver — **not** a doubled crew.
- Above `shuttleMaxMiles`, disable Option 1: *"Too far to shuttle."*

**Case B — WEIGHT over payload but volume fits (soft).** Warn only. **Default stays 1 truck** and the quote prices normally; the owner may manually escalate to 2 trips or 2 trucks.
- **Banner:** *"Estimated weight is near the payload limit (9,770 lb vs 9,000 lb) — verify on survey."*

This distinction matters: **every** truck-split in the acceptance run was weight-only with volume fitting comfortably (Case 2: 1,460 of 1,500 cu ft; Case 8: 1,400; Case 9: 1,200). Weight is an estimate, and 9,770 vs 9,000 is inside estimation error — auto-splitting on it doubled the trip fee and inflated every heavy 3BR quote. Do not let a weight estimate spend a second crew.

### P1-2. Commercial mode — full build

**Build:**

3. **Commercial defaults to flat/quoted pricing** with a **required survey** — no firm number without one.

4. **Commercial access conditions:** freight elevator reservation, loading dock, **certificate of insurance (COI) required**, after-hours / weekend building access.

### P1-3. Long-distance handling

## FINALLY — build the calibration loop

The calculator has a control labeled "Man-hours per 100 cu ft" (currently 2.10) with the note: *"Log actual man-hours ÷ surveyed cu ft on every job and move this to match reality after ten of them."* **That loop does not exist.**

Build it:
- On job completion, capture **actual man-hours** and **actual surveyed cu ft**; store both against the job.
- Show the owner a rolling estimated-vs-actual comparison.
- After 10+ completed jobs, surface a suggested calibration value (separately for residential and commercial).

Every other item in this spec corrects a logic error. None of them can tell us whether 2.10 mh/100 cu ft matches how these crews actually work — and that single number drives every labor dollar in the system. Ship it with Deploy 2.
